# Piano: Queue + Heartbeat Worker per le RUN
**Data:** 2026-04-28  
**Autore:** Claude (Sonnet 4.6)

## Obiettivo
Sostituire l'esecuzione sincrona monolitica delle RUN con un sistema a coda (FIFO) e un daemon worker che processa un item alla volta, con timeout per item, stato persistente e possibilità di resume/retry selettivo per modello.

## Architettura

### Tipi di operazione in coda (in ordine di priorità)
| Tipo | item_key | Timeout | Descrizione |
|---|---|---|---|
| `snapshot_translations` | `"snapshot"` | 15s | Freeze translated candidates |
| `magi_phase2` | `"magi:c{candidate_id}"` | 150s | Panel MAGI giudici per candidato flagged |
| `llm_call` | `"llm:p{P}:l{L}:m{M}"` | 120s | Chiamata LLM singola |
| `compute_pei` | `"pei:p{P}"` | 45s | PEI per singolo prompt |
| `finalize_pei_groups` | `"finalize_pei"` | 30s | Calcola baseline gruppi PEI per tutta la run |

### Stati di un item
`pending` → `running` → `done` | `error` | `timeout`

### Stati di una RUN (`experiment_runs.status`)
`queued` → `running` → `completed` | `partial` | `failed`

## Note implementative
- Il `QueueService` usa il suo proprio `DatabaseManager` (come `LogService`), rilegge le settings dal DB a ogni operazione per supportare aggiornamenti delle API key in corsa.
- `enqueue` è idempotente (`INSERT OR IGNORE`) sulla chiave `(run_id, operation_type, item_key)` — sicuro in caso di doppio submit.
- `recover_stale_running()` all'avvio resetta a `pending` tutti gli item `running` rimasti da un crash precedente.
- Il resume non riprocessa item `done` — parte da dove si era fermato.
- Il retry per modello legge il campo `model_id` dal payload JSON dell'item.
